# Porter control-plane API v1 contract

## Status

This is the target contract for the Vue/PostgreSQL migration, not a claim of full API parity. The root server mounts PostgreSQL-backed `/api/v1` only when `PORTER_POSTGRES_API_DSN` is explicitly set and migrations 0001–0007 already exist. Without that setting, `/api/v1` returns `503 failed_precondition`; it never falls back to SQLite. Legacy `/v1` routes continue using SQLite during this phase. The Vue Overview, Projects, Services, Fleet, Domains, Storage, Backups, and Operations/Events pages use the implemented PostgreSQL flow; other routes remain unmigrated.

The Go wire types are in [`porter/contract/v1`](../porter/contract/v1/types.go). The browser calls the Go API only; PostgreSQL credentials stay server-side.

## Resource model

```text
Project
└── Service
    ├── Release
    │   └── Instance (one-based ordinal; placed on a Fleet node when scheduled)
    │       ├── Operation → AgentCommand → AgentCommandResult (persistence only)
    │       └── SnapshotMetadata (capture unavailable)
    │           └── BackupMetadata (off-host storage unavailable)
    ├── Volume (single-writer declaration only)
    └── DomainClaim
        └── GatewayRoute (saved desired intent only)
```

A Project is a named grouping. A Service is a deployable workload with desired capacity and resource settings. A Release records the requested source selector, a resolved immutable source commit, a build definition, and—after a successful isolated build—a content-addressed artifact. Instances are Firecracker guests created from a Release. Volumes, snapshots, and backups in this slice are metadata records only. Fleet nodes are operator-managed placement targets, not customer projects or tenants.

IDs are opaque strings generated by the control plane. Clients must not parse them or assume a UUID format. Timestamps use RFC 3339 with UTC offsets. JSON uses `snake_case` field names, matching the Go `json` tags and PostgreSQL columns.

For Git-backed Releases, `source.ref` is selection metadata only (for example, the requested branch or tag `main`); it is not the revision built. While the Release is `building`, the control plane resolves that selector, records `resolved_commit` as a lowercase 40- or 64-character Git object ID, and checks out/builds that exact commit. A later movement of the requested branch does not change the Release. If resolution fails, the Release becomes `failed`.

## Authentication and scope

When the PostgreSQL adapter is enabled, every `/api/v1` route requires `Authorization: Bearer <control-plane-admin-token>`. When it is disabled, the prefix returns the documented 503 envelope. This first contract defines one operator/admin capability set; it does not add customer accounts, reseller accounts, organizations, or multi-tenant RBAC. Legacy agent enrollment and `/v1/fleet/*` SQLite routes remain unchanged.

## Separate internal agent v2 transport

The following routes are internal agent plumbing, not `/api/v1` product routes. They mount only when `PORTER_AGENT_V2_ENABLED=true`, the API listener has `PORTER_API_TLS_CERT` and `PORTER_API_TLS_KEY`, `PORTER_POSTGRES_API_DSN` points to the control-plane database, and migration 0007 has already been applied explicitly. Startup never runs migrations. V2 always requires HTTPS, including loopback.

| Method and path | Purpose | Authentication |
| --- | --- | --- |
| `POST /internal/admin/fleet/enrollment-tokens` | Issue a one-time token for an operator-selected same-host or remote-agent target; returns it once with `Cache-Control: no-store` | Operator Bearer token |
| `POST /internal/agent/enroll` | Redeem a short-lived token and atomically create/bind a Fleet node plus its v2 credential | One-time enrollment Bearer token |
| `POST /internal/admin/fleet/nodes/{node_id}/credentials` | Provision or rotate a per-node credential; returns the plaintext once with `Cache-Control: no-store` | Operator Bearer token |
| `POST /internal/agent/heartbeat` | Update last-seen time; an offline node may become ready | Node Bearer token and `X-Porter-Node-ID` |
| `GET /internal/agent/commands?limit=1` | Requeue that node's expired leases and lease typed VM lifecycle commands | Node Bearer token and `X-Porter-Node-ID` |
| `POST /internal/agent/results` | Submit a node-, operation-, kind-, attempt-, and lease-fenced result | Node Bearer token and `X-Porter-Node-ID` |

Only SHA-256 hashes of random enrollment and node tokens are stored in PostgreSQL. Enrollment tokens expire after ten minutes, are single-use, and bind the selected topology and HTTPS control-plane origin to the newly created node. The response includes the node token once; the opt-in agent `join --protocol-version v2` stores it in a local owner-only file and saves no secret in local SQLite config. V1 `join` remains the default and unchanged. Credential rotation can retain the previous node token for a bounded grace period (five minutes by default). The agent must explicitly select `run --protocol-version v2` and enable `--enable-v2-dispatch true` or `PORTER_AGENT_V2_DISPATCH=true`. The v2 client accepts only `vm.apply`, `vm.delete`, `vm.start`, `vm.stop`, and `vm.restart`; it has no shell-command executor. Dispatch also requires Linux, an accessible KVM API v12 device, and a Firecracker binary. Automated tests use a fake runtime; no real Firecracker/KVM acceptance is claimed. The Fleet UI never installs or starts agents or runs a remote command; the Firecracker API socket remains local to each agent host.

When enabled, the root server exposes Project/Service list, get, and create routes; Release/Instance list and get routes; read-only Fleet-node, operation, and resource-event collections; PostgreSQL-backed domain claim, TXT verification, and preview route-intent routes; and metadata-only volume, snapshot, and backup routes.

`POST /api/v1/services/{service_id}/releases` validates the request but currently returns `412 failed_precondition`; it does not insert a queued Release or start a build. It stays disabled until the isolated Firecracker builder, queue, and rollout worker are ready. Fleet nodes, operations, and events are read-only in `/api/v1` except that unsupported operation retry/cancel/dispatch paths return explicit `412 failed_precondition`. `/api/v1` does not expose operation creation, enrollment, heartbeat, agent polling, result submission, or event writes; the separate internal v2 transport is described above. New Fleet-node rows start `offline` with no `last_seen_at`; a persisted row is not proof that an agent is connected.

A successful resource creation response includes a `Location` header. Collection responses always use `{ "items": [...], "next_cursor": "..." }`; `next_cursor` is omitted on the last page. Lists accept `page_size` and an opaque, signed cursor scoped to its collection and parent resource. The default page size is 50, the maximum is 100, and pages use database keyset pagination: most resource collections use `(created_at ASC, id ASC)`, Releases use `(sequence DESC, id ASC)`, and events and operations use descending time/ID order. Cursors become invalid if the operator token changes. Invalid page sizes or cursors fail with `400 bad_request`.

Domain claims are attached to one exact Project/Service pair; the database uses composite foreign keys to prevent a claim or route from pointing at a Service in another Project. The API canonicalizes the hostname and returns a manual TXT name/value. It performs DNS TXT reads only. A claim becomes `verified` only after the server resolver observes the exact challenge and stores that observed value and timestamp in PostgreSQL. Missing or mismatched TXT data does not persist proof. Provider DNS writes are not integrated.

Gateway routes store only `desired_enabled` configuration. PostgreSQL rejects enabling route intent until the claim has persisted TXT proof, but `gateway_status` remains `unavailable`: there is no gateway reconciler, live traffic routing, ACME, or TLS automation in this slice. Enabling a saved intent does not change traffic or promise that the domain is reachable. The Domains UI labels these controls as preview-only.

Storage routes persist only declarations and metadata. A Volume is `single_writer` and `metadata_only`; shared-writable claims are rejected. A node-affinity ID is a saved placement hint only; no disk is provisioned, mounted, resized, attached to an Instance, cloned, or deleted. Snapshot metadata is scoped to one existing Project/Service/Instance and accepts only `crash_consistent`; `capture_status` and `integrity_status` remain `unavailable` and `not_available`, with no artifact digest, size, or verification timestamp. Backup metadata must reference that exact snapshot scope; it remains `metadata_only`, `off_host_status: unavailable`, and integrity-unverified. These POST routes create database records only. They do not capture VM disks, copy data off-host, restore data, or recover a workload. The UI does not offer capture/restore controls.

The event stream is append-only and records resource changes in the same PostgreSQL transaction as the resource write. Each `Event` has an `id`, `type`, `occurred_at`, optional `project_id`, `service_id`, `release_id`, `instance_id`, `fleet_node_id`, `domain_claim_id`, `gateway_route_id`, `volume_id`, `snapshot_id`, `backup_id`, `operation_id`, or `command_id`, and a structured JSON `data` object. Operation/command events record state, kind, attempt, and result-state metadata; they never include lease tokens or command payloads. The stream is global to this single-operator control plane; it does not yet provide filters, retention controls, or tenant isolation. Event payloads avoid source URLs, build credentials, failure text, and other secret-bearing values.

A release request has this shape:

```json
{
  "source": {
    "kind": "git",
    "repository": "https://example.invalid/team/service.git",
    "ref": "main"
  },
  "build": {
    "kind": "dockerfile",
    "dockerfile_path": "Dockerfile"
  }
}
```

Or, for the supported Compose build-input subset:

```json
{
  "source": {
    "kind": "git",
    "repository": "https://example.invalid/team/service.git",
    "ref": "main"
  },
  "build": {
    "kind": "compose",
    "compose_file": "compose.yaml",
    "primary_service": "web"
  }
}
```

The response `Release` keeps the requested ref and resolved revision separate:

```json
{
  "source": { "kind": "git", "repository": "https://example.invalid/team/service.git", "ref": "main" },
  "resolved_commit": "0123456789abcdef0123456789abcdef01234567"
}
```

Build inputs are not production container workloads. Builds must run in isolated, disposable Firecracker builder MicroVMs. The builder accepts only the explicitly supported single-primary-service Compose subset and must reject unsupported features. No host-Docker or unisolated fallback is allowed; source builds stay disabled until that boundary passes its acceptance gate. Production instances run only as Firecracker/KVM MicroVMs.

## Operations and agent-command persistence

Migration `0005_operations_command_leases.sql` persists operation, command-lease, and result-receipt metadata in PostgreSQL. Operations are scoped to an exact Project/Service/Instance tuple and use `queued`, `running`, `succeeded`, or `failed`. A project-scoped idempotency key is bound to a SHA-256 fingerprint of the full typed request; reusing the key with different content conflicts, and only one active operation may exist per Instance.

The command kind is a closed allowlist: `vm.apply`, `vm.delete`, `vm.start`, `vm.stop`, `vm.restart`, `snapshot.create`, `snapshot.restore`, and `volume.resize`. Store methods accept kind-specific Go payload types; unknown kinds, raw command strings, and arbitrary shell commands are rejected. A lease attempt gets a fresh random token, but only its SHA-256 hash is persisted. An expired lease returns to `queued` without changing the attempt; the next lease increments it. A result is accepted only for the current node, operation, attempt, matching command kind, unexpired token, and kind-specific result state. Identical duplicate results are idempotent; stale attempts/tokens and conflicting duplicates are rejected. Result receipts and matching operation/command events commit atomically and are append-only.

Operation creation and retry/cancel/dispatch are not exposed as `/api/v1` product routes. Authenticated enrollment and agent poll/result routes exist separately under the internal v2 transport, but mount only behind its explicit HTTPS, PostgreSQL, migration, and opt-in gates above. The active `/v1/fleet/commands` and `/v1/fleet/result` endpoints still use the unchanged v1 messages; they do not accept or dispatch v2 commands. The UI exposes safe operation summaries and a manual v2 enrollment flow only; it never runs a remote install/start command. Tests use a fake runtime, so real Firecracker/KVM acceptance and remote production operation remain unverified. Storage capture/restore and other unsupported side effects remain unavailable.

## Lifecycle rules

- Projects and Services start `active`; deletion, when implemented, moves them to `deleting`. Deletion is not a hard delete while child records exist.
- Releases move through `queued → building → ready → deploying → active`. During `building`, resolve `source.ref` and pin `resolved_commit`; `ready`, `deploying`, `active`, and `superseded` are invalid without that pin. Once set, `resolved_commit` cannot change. A failed stage becomes `failed`; when a successor becomes active, the old active release becomes `superseded`. At most one release per service is `active`.
- Instances start `pending`, then normally become `provisioning` and `running`. They may become `stopped`, `failed`, `deleting`, or terminal `deleted`. `health` is `unknown`, `healthy`, or `unhealthy` and is distinct from lifecycle state.
- `runtime` is always `firecracker` for production Services and Instances. KVM is the required host capability; Docker/Compose is only an input format for an isolated builder.
- Instance ordinals start at 1 and are unique within one Release. Scaling changes a Service's `desired_instances`; it does not mutate a Release's source or artifact.

## Errors

Errors use one envelope:

```json
{
  "error": {
    "code": "conflict",
    "message": "a release is already being deployed",
    "request_id": "req_..."
  }
}
```

`request_id` may be omitted. Stable codes are `bad_request`, `unauthenticated`, `permission_denied`, `not_found`, `conflict`, `failed_precondition`, `rate_limited`, and `internal`. The HTTP status is authoritative: normally 400, 401, 403, 404, 409, 412, 429, and 500 respectively. Do not expose SQL, credentials, or host secrets in `message`.

## Events

`Event` is a versioned JSON envelope with `id`, `type`, `occurred_at`, the applicable resource IDs, and an object-valued `data` payload. Event types use `<resource>.<action>` names, such as `release.build_started`, `domain_claim.verified`, `gateway_route.desired_state_changed`, or `instance.failed`. Event IDs are opaque; event order is the server-assigned durable order, not client time. `GET /api/v1/events` reads the persisted append-only stream with descending keyset pagination; filtering by resource ID is not implemented. The Overview activity view uses this real stream rather than sample data.

## Go types

`porter/contract/v1` is the source of truth for Go resource, request, page, error, and event wire shapes. It intentionally contains no HTTP handlers or database access. When routes are implemented, handlers must use these types rather than define per-view compatibility DTOs.
